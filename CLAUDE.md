## Architecture

Flat 3-layer architecture with no external state manager — `StreamBuilder` + `setState` throughout.

```
lib/
  main.dart               # App entry point: Firebase init, theme, auth routing
  firebase_options.dart   # Generated by FlutterFire CLI — do not edit manually
  models/                 # Pure Dart data classes (fromDoc/toMap, no business logic)
  services/               # All side effects live here (Firebase, Auth, PDF, notifications)
  screens/                # Full-page widgets, one per route
  widgets/                # Reusable sub-widgets
```

### Data flow

The root `StreamBuilder` in `main.dart` listens to `FirebaseAuth.authStateChanges()` and routes to `MainScreen` (bottom navigation: Início/`HomeScreen`, Relatório/`RelatorioScreen`, "Mais" sheet) or `LoginScreen`. All Firestore access goes through `GlicemiaService`, which scopes every query to the current user's `uid`. Screens call service methods directly — there is no intermediate ViewModel or Provider layer.

### Key services

- **`GlicemiaService`** — sole Firestore accessor. Paths: `usuarios/{uid}/registros`, `usuarios/{uid}/perfil/paciente`, `usuarios/{uid}/refeicoes`.
- **`AuthService`** — wraps `FirebaseAuth` + `GoogleSignIn` + `sign_in_with_apple`. Supports email/password, Google, Apple, password reset, and account deletion (revokes the Apple token).
- **`NotificacaoService`** — local notifications via `flutter_local_notifications` + `timezone`.
- **`PdfService`** — generates PDF reports from `RegistroGlicemia` lists using the `pdf` package.
- **`AnalyticsService`** — thin wrapper around `firebase_analytics`; its `NavigatorObserver` is registered in `main.dart`.
- **`AdsService`** — UMP consent → ATT (iOS) → `MobileAds.initialize()`, plus the interstitial. Started from `MainScreen` after the first frame (post-login).

### Authentication note

There is no anonymous sign-in: users must log in (email, Google, or Apple) before reaching `MainScreen`. Sign in with Apple requires the `Runner.entitlements` capability, which needs a paid Apple Developer team (a Personal Team cannot sign it).

### AdMob

Ads use Google test IDs in debug (`kDebugMode`) and production IDs in release.

- **Banner** — a single `AdBanner` in `MainScreen` above the `NavigationBar`, shared by both tabs. Do not add banners inside `IndexedStack` children (hidden banners load). It waits for `AdsService.pronto` and only occupies space after a successful load.
- **Interstitial** — shown only before sharing the PDF in `RelatorioScreen`, with a 3-minute cooldown. Production unit IDs live in [lib/services/ads_service.dart](lib/services/ads_service.dart); while empty, the interstitial is disabled in release.
- **Consent** — the GDPR message must be published in the AdMob console (Privacy & messaging), otherwise no form appears. Test it with `flutter run --dart-define=ADS_EEA=true`; on a physical device also pass `--dart-define=ADS_TEST_DEVICE=<id>`, using the id the UMP SDK logs ("UMPDebugSettings.testDeviceIdentifiers" in the Xcode console on iOS). The "Privacidade dos anúncios" entry in the Mais sheet appears when UMP requires it.
- **app-ads.txt** — served from `https://rogerinhoduraes.github.io/app-ads.txt` (repo `rogerinhoduraes.github.io`); the store listings' Website must point to that domain.

### Android release signing

The release build reads `android/key.properties` (gitignored). Structure:
```
storePassword=...
keyPassword=...
keyAlias=...
storeFile=path/to/keystore.jks
```

### Firestore security rules

`firestore.rules` restricts each user to `usuarios/{uid}/**` (requires `request.auth.uid == uid`). Deploy changes with `firebase deploy --only firestore:rules`.
